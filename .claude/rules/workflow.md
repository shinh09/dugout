# 작업 방식

- 수정 전에 관련 코드와 `docs/design` 설계 문서를 먼저 읽는다
- 구현 전에 계획을 보여준다(`/plan`). 파일 5개 이상 바뀌는 변경은 승인 후 진행한다
- 한 번에 이슈 하나만, 변경은 그 이슈 범위 안에서만 한다
- 기존 코드의 구조·이름·패턴에 맞춘다. 잘 동작하는 코드를 다시 쓰지 않는다(리팩터링은 별도 이슈)
- 새 의존성을 임의로 추가하지 않는다. 필요하면 이유와 대안을 제시하고 승인받는다
- 파일 삭제, DB 테이블·컬럼 삭제, 대량 코드 삭제는 먼저 묻는다
- TODO나 "나중에" 주석을 남기지 않는다. 범위 밖 작업은 GitHub 이슈로 만든다
- 끝나면 바꾼 것(파일·이유·테스트 결과)을 요약한다
- 모르거나 확실하지 않으면 추측하지 말고 그렇다고 말한다
